# PR CR 群说明生成器

把一个 PR 翻译成**给产品/评审同事看的群消息**。五段固定结构：背景 / 做了啥 / 目的 / 影响范围 / 注意验收的事项。

## 铁律：纯产品语言，零技术术语

读者是产品/设计/评审同事，不是写代码的人。**绝对不要**出现下列任何东西：

- 代码概念：字段名、变量名、函数名、组件名、文件路径、API/接口、端点、数据库、metadata、baseDir、linkedDirs、props、CSS、SDK、组件、参数、配置项……
- 工程动作：重构、抽组件、改字段、加端点、typecheck、打包、合并、迁移……
- 任何英文技术词、驼峰命名、`代码块`、`/路径/`。

要用**用户能看到、能感知**的话来描述：用户点了什么、看到什么、哪里变了、体验有什么不同。

自检：写完通读一遍，凡是非本团队产品同事一眼看不懂的词，全部换成大白话；换不掉的就删掉那句。

## 步骤

1. **拿到 PR 信息**（用户没给链接时自己查）：
   - 当前分支的 PR：`gh pr view --json number,title,url,body,headRefName`
   - 或指定编号：`gh pr view <号> --repo <owner/repo> --json number,title,url,body`
   - 看改动范围：`gh pr diff <号>` 或 `git diff origin/main...HEAD`（**只用来理解改了什么，不要把代码细节写进输出**）。

2. **想清楚"用户视角发生了什么"**：这次改动让用户在产品里多了/少了/变了什么？从"用户打开产品会怎样"倒推，而不是从"代码改了哪里"正推。

3. **判断影响范围**：这次改动除了目标功能，还会碰到哪些**相邻功能/场景**？哪些**明确不受影响**？想清楚连带改动、共用入口、改了默认行为会让老用户察觉的地方。用产品语言列，不写代码层面的依赖。

4. **按五段写**（见下方模板），中文，群聊口吻，简洁不啰嗦。

5. 写完**做一次术语自检**（见上面铁律），再交付。

6. 主动补一句：可以再给一版**更短的三两句摘要**（放群里当引子，详情点链接看）。如果群里 Markdown 不渲染，可给纯文本版（去掉加粗/emoji）。

## 输出模板

```
📦 PR #<号> · <一句话产品标题>
🔗 <链接>

**1. 背景**
<现在用户遇到的问题 / 当前体验哪里别扭，用大白话讲清楚为什么要做这件事>

**2. 做了啥**
<用户能直接感知到的变化。按界面/场景分条：用户在哪里、点什么、看到什么变了。每条都站在用户角度。>

**3. 目的**
<这次改动想达成的产品价值 / 想让两件事/体验变成什么样。一两句讲透。>

**4. 影响范围**
<这次改动会连带影响到哪些相邻功能/场景，要分两类列：>
<- 可能受影响：<连带变化的功能、共用同一个入口的地方、改了默认表现老用户会察觉的点>>
<- 不受影响：<容易被担心、但这次明确没动的功能，逐条点名让大家放心>>

**5. 注意验收的事项**
<评审/测试的人该重点确认哪些点。每条都是"做某个操作 → 应当看到某个结果"的可验证描述，覆盖正常流程 + 边界 + 容易被忽略的地方。可标 ✅。>
<如有不在本次范围内、容易被误以为也改了的东西，用 ⚠️ 单列一条说明"本次没动"。>
```

## 风格要点

- 标题用产品语言概括价值，不是 commit 标题照搬。
- 「做了啥」按用户能看到的界面/动作分条，不按代码模块分。
- 「验收事项」要可操作：写成"做 X → 应当 Y"，让人照着就能验。
- 句子短、可扫读；多用动词，少用形容词。
- 默认中文。除非用户要求，否则不加技术附录。
