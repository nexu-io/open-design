# Proposal: Token Bridge — Cookie-Based Access Token for Docker/Proxy Deployments

**Status:** draft
**Created:** 2026-06-11

## Problem Statement

When the daemon runs in Docker (or behind any reverse proxy) with `OD_ACCESS_TOKEN` set, the web UI cannot make any `/api/*` requests because:

1. **Loopback check fails in Docker**: The browser connects to `localhost:PORT` (mapped to container port), but Docker rewrites the source IP to the bridge gateway (`172.17.0.1`). `isLoopbackPeerAddress()` returns `false`, so the loopback bypass in the access-token middleware does not apply.

2. **No Bearer token is sent**: The web UI's `fetch()` calls to `/api/*` never include an `Authorization: Bearer` header. The web UI has no mechanism to discover the `OD_ACCESS_TOKEN` value.

3. **Cascading failure**: The web UI loads the initial HTML successfully (SPA fallback served by the daemon), but every `/api/*` call during startup returns 401. The app never reaches a functional state — no config, no projects, no CLI detection, no agents.

### Symptoms

All `/api/*` endpoints return 401 in the browser DevTools console:

```
/api/app-config:1           Failed to load resource: 401
/api/agents?stream=1:1      Failed to load resource: 401
/api/projects:1             Failed to load resource: 401
/api/media/config:1         Failed to load resource: 401
/api/connectors:1           Failed to load resource: 401
... (20+ endpoints)
```

Even though `/api/agents` is an open probe path (from the `fix-cli-detection` change), the app cannot reach a functional state because `/api/app-config`, `/api/projects`, `/api/templates`, and all other config-loading endpoints are blocked.

### Scope of impact

- **Docker deployments** with `OD_ACCESS_TOKEN` set (auto-generated by `install.sh` or user-provided)
- **Reverse proxy deployments** where the browser connects through a proxy and the daemon sees a non-loopback remote address
- **Not affected**: Local dev (`tools-dev`) because the browser connects directly to `127.0.0.1` (loopback) and the access-token middleware allows loopback callers without a token
- **Not affected**: Trusted-proxy mode with Cloudflare Access because the browser sends `Cf-Access-Jwt-Assertion` header automatically

## Proposed Solution

### Cookie-based token delivery

When serving the initial HTML page (the SPA index.html), the daemon sets a `Set-Cookie` header with the access token:

```
Set-Cookie: od_access_token=<token>; Path=/; SameSite=Lax
```

The browser stores this cookie and automatically includes it in all subsequent same-origin requests. The daemon's access-token middleware checks for this cookie **before** returning 401.

### Three-step implementation

#### Step 1: Daemon injects cookie on HTML response

Modify the `express.static` configuration in `server.ts` to set the `od_access_token` cookie when serving `index.html` files:

```typescript
app.use(express.static(STATIC_DIR, {
  setHeaders: (res, filePath) => {
    if (accessToken && filePath.endsWith('index.html')) {
      res.setHeader('Set-Cookie', 
        `od_access_token=${accessToken}; Path=/; SameSite=Lax`);
    }
  },
}));
```

Also add the same cookie to the SPA fallback handler (`registerStaticSpaFallback`).

#### Step 2: Daemon middleware accepts cookie token

Modify the access-token middleware in `server.ts` to accept the cookie as an alternative to the `Authorization: Bearer` header:

```typescript
// After loopback check, before Bearer check:
const cookies = parseCookies(req.get('cookie') ?? '');
const cookieToken = cookies['od_access_token'];
if (cookieToken && cookieToken === accessToken) return next();
```

A lightweight `parseCookies` helper is added to avoid pulling in the `cookie-parser` dependency.

#### Step 3: Tests

Add unit tests to `apps/daemon/tests/api-token-guard.test.ts`:
- Cookie with valid token → 200
- Cookie with invalid token → 401
- Cookie with valid token but wrong value → 401
- No cookie, no Bearer, non-loopback → 401 (regression)
- Cookie present but `OD_ACCESS_TOKEN` unset → cookie ignored, loopback check applies (no crash)

### Token lifecycle

| Event | Cookie state |
|---|---|
| Browser loads `localhost:PORT` | Daemon sets `od_access_token` cookie |
| Browser makes `/api/app-config` | Cookie sent automatically, middleware accepts |
| User changes `OD_ACCESS_TOKEN` and restarts daemon | Old cookie invalid → 401 → user clears cookies or browser detects mismatch |
| Token rotation (future) | New cookie overwrites old on next page load |

### Security considerations

- **SameSite=Lax**: Cookie is not sent on cross-site requests. Prevents CSRF-based API access from other origins.
- **No HttpOnly flag**: The cookie must be readable by JavaScript for potential future client-side use (e.g., copying the token for CLI tools). The risk is minimal because the cookie value is the same secret already exposed via the `OD_ACCESS_TOKEN` env var.
- **No Secure flag**: Not set because Docker deployments often use plain HTTP on localhost. Operators using HTTPS behind a proxy should already have TLS termination at the proxy.
- **Path=/**: Cookie is scoped to the entire origin, covering all `/api/*` paths.
- **No Expires/Max-Age**: Session cookie. Cleared when the browser closes. This is appropriate for a daemon that may restart with a new token.

## Scope

**In scope:**
- Daemon: inject `od_access_token` cookie on HTML responses (static serving + SPA fallback)
- Daemon: check cookie in access-token middleware
- Daemon: lightweight `parseCookies` helper
- Tests: unit tests for cookie auth flow
- Deploy: no changes needed (docker-compose.yml, install.sh, etc. — transparent)

**Out of scope:**
- Removing or modifying the existing `Authorization: Bearer` header check
- Changing the Cloudflare Access middleware
- Adding token UI (login form, token display in settings)
- Token rotation mechanism
- Making `HttpOnly` or `Secure` flags dynamic (out of scope for this fix; can be added later via env var)
- Web UI changes (the browser sends cookies automatically)

## Risks

- **Stale cookie on token rotation**: If the daemon restarts with a new token, the browser still has the old cookie. The old cookie will fail validation (401). The user must close and reopen the browser tab, or the daemon could detect the failure and re-set the cookie on the next HTML response. **Mitigation**: Document this behavior. Future: add a `401 → redirect to /?reauth=1` flow.

- **Cookie sent to non-API paths**: The cookie is sent with every same-origin request, including static assets. This is harmless (the static asset middleware ignores cookies). No performance impact.

- **Multiple daemon instances on same origin**: If two daemons share the same origin (unlikely — they'd be on different ports), cookies would conflict. **Not a realistic scenario** in current architecture.

## Non-Goals

- Web UI login page or authentication UX
- Token rotation or expiration
- Making the cookie `HttpOnly` or `Secure` configurable
- Changing the Cloudflare Access flow
- CLI-to-daemon auth (CLIs authenticate via installed credentials, not this cookie)
