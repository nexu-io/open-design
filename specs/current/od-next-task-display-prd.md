# 会话任务进度与执行记录优化

## 背景

一次设计任务可能先生成计划，再自动进入制作。当前会话会分别显示各阶段的“已完成／进行中”和耗时：计划刚结束，用户就看到一次“已完成”；制作开始后，又出现新的状态和计时。

用户关心的是整项任务是否还在执行、累计用了多久，以及最后的结果。阶段分别结算的展示容易让人误以为任务已结束，也难以直观了解总耗时。规划和制作的拆分属于后台策略，前端无需通过多个执行记录入口让用户感知这项拆分。

## 目标

- 同一项任务只展示一份总体状态、一份累计耗时和一个执行记录入口。
- 从规划进入制作时，状态连续、计时不归零。
- 用户能清楚区分正在执行、等待回答和最终结束。
- 完整执行过程仍可查看，待回答的问题和最终产物保持清晰可见。

## 方案

### 统一任务状态

在助手名称下显示一条任务状态，贯穿本次任务。沿用现网的状态图标、文案和排版；内部切换执行阶段时保持“进行中”，不显示中间的“已完成”。最后结束时，根据实际结果显示最终状态。

| 场景 | 用户看到的状态 |
| --- | --- |
| 任务尚未开始执行 | 准备中 |
| 正在规划、制作，或自动衔接下一阶段 | 进行中 |
| 需要用户补充信息 | 等待回答 |
| 回答已提交并被接受，正在等待恢复执行 | 准备中 |
| 任务成功结束，且没有待回答问题或待继续内容 | 已完成 |
| 本次执行结束，仍有可继续的内容 | 任务尚未完成 |
| 执行失败或用户取消 | 运行失败／已取消 |

### 累计任务耗时

任务开始执行后持续累计。自动切换阶段的衔接时间计入，进入制作时不重新计时。

等待用户回复时暂停；恢复执行后接着累计。最终结束时冻结总耗时。刷新页面、切换会话再返回或重新连接后，继续显示原来的状态和累计时间。

例如，规划 12 秒、自动衔接 2 秒、制作 28 秒，最终显示 42 秒；中途等待用户回复的时间不计入。

### 统一执行记录

同一项任务只保留一个“执行记录”入口。自动规划说明、思考和工具动作按发生顺序汇总在其中。进入制作、重试或恢复时，继续追加到这份记录，不另开入口，不按后台执行轮次分段显示状态与总耗时。

任务执行中默认展开；等待回答或任务结束后默认收起。用户手动展开或收起后，后续切换阶段、恢复执行和刷新继续尊重该选择。没有过程内容时，不展示空的执行记录。

工具和步骤自己的进度继续保留。需要用户确认的方案、问题、已提交的回答、失败原因与恢复操作、最终结论和产物入口留在记录外，保持会话中的先后顺序，收起记录也不会隐藏这些内容。

### 明确任务边界与恢复

原问题的回答和明确的续做操作可以延续本任务的状态与计时。普通新请求单独开始一项任务，不因引用旧内容而自动合并。

失败、取消和任务尚未完成时，保留相应原因及可用的恢复操作。仅连接异常时不误报任务已完成或失败；恢复连接后按实际状态更新。历史记录无法确定总耗时时，保留状态，不展示猜测的时间。

## 预期表现

- 用户从规划到制作始终看到同一份“进行中”和连续增长的累计时间。
- 同一任务始终只有一个执行记录入口，后台切换执行轮次不会新增记录卡片；展开可查看完整过程。
- 只有任务最终结束时才出现一次最终状态，规划完成不会被误认为整项任务完成。
- 等待回答期间显示“等待回答”，秒数停止；回答被接受后显示“准备中”，恢复执行后秒数继续增长。
- 自动规划说明归入执行过程；需要用户处理的问题与方案、最终结果始终可见。
- 刷新、返回会话或恢复任务后，状态与累计时间延续；新的用户请求使用独立状态和计时。

本需求适用于 Web 和桌面客户端的会话展示。交互 Demo 使用演示数据说明预期体验，不代表功能已经上线。
