# OD Next 会话任务状态与累计计时

## 背景与目标

同一用户任务可能先规划，再由宿主自动进入生产。当前源码已把多次 Run 合成一条助手回答，但各次 Run 的执行记录仍分别显示“已完成／进行中”和自己的耗时。用户容易将规划结束理解为任务已完成，也会看到计时重新开始。

本次改为：**同一任务只展示一份任务状态、一份累计耗时和一个执行记录入口。自动切换 Run 时保持进行中，计时不归零，过程继续追加到同一记录；任务最终结束后只显示一次最终状态。** 本文的“任务”指前端一次用户请求及其明确的回答、续做所构成的展示任务，由宿主确认归属；Run 指一次底层 Agent 执行。底层执行任务 ID 可以变化，不直接决定是否另开一份展示状态或过程入口。

本轮交付方案与评审，不实现代码、不提交 PR。

验收目标是确定性的：每项适用任务在默认视图中只有一个任务状态入口、一个任务累计计时，有过程内容时只有一个执行记录入口；自动交接期间不出现中间完成状态、计时归零或第二个过程入口。用户体验改善的线上目标值与观察周期尚未明确，本轮不编造提升比例。

## 需求概览

| 编号 | 本次改变 | 改动范围 |
| --- | --- | --- |
| R1 | 宿主明确展示归属，同一任务只展示一份总体状态，中间 Run 结束不宣告任务完成 | Web、桌面客户端、服务端 |
| R2 | 同一任务连续累计耗时，自动衔接计入，等待用户回答暂停 | Web、桌面客户端、服务端事实投影 |
| R3 | 全任务过程汇总到一个执行记录入口，自动规划说明归入过程；待确认内容、问答与结果保持会话顺序 | Web、桌面客户端 |
| R4 | 刷新、断线重连、切换会话及历史回放保持同一状态与计时口径 | Web、桌面客户端、服务端事实投影 |
| R5 | 失败、取消、尚未完成和恢复显示明确，不能用规划完成覆盖生产结果 | Web、桌面客户端 |

这是现有会话展示调整，需要新增可恢复的展示归属和计时事实。底层执行任务划分、执行策略、模型输出要求、权限与工具复用现有能力；不会因为展示合并而把底层任务合成一个。

## 展示规则

### 展示任务归属

- 自动后继 Run 延续原展示任务。
- 用户通过原问题表单提交答案，宿主核实来源问题与所属项目、会话后，延续原展示任务。即使回答创建了新的底层执行任务，状态与累计计时也延续。
- 明确的“继续剩余任务”、重试或恢复操作，在宿主核实来源与可恢复性后延续原展示任务；操作被判定为新任务时单独展示。
- 普通输入框的新请求另开展示任务，即使带有前一个任务的历史上下文，也不自动合并。不通过自然语言相似度判断“是不是同一需求”。
- 缺少可靠来源的旧关联不猜测合并；跨项目、跨会话或伪造来源不建立展示关联，沿用现有拒绝与错误反馈。

### 一项任务、一份状态

- 只按上述宿主确认的展示归属合并状态和计时；同一项目或同一 analytics 标识不构成合并依据。
- 统一状态行放在助手名称下、过程与正文前。沿用现网运行中的旋转图标、“进行中”动效文案与耗时排版，只把计时口径改为整项任务累计；不新增“任务执行”字样或状态圆点。
- 展示任务的首个可见助手回复承载唯一状态行；同任务的后继回复不重复状态行。物理消息暂未合并、后继边界延迟时仍只有这一份状态；局部历史未含原首条回复时，由当前最早可见回复承载。
- 不在阶段执行记录或回答页脚重复总体“进行中／已完成”和任务累计耗时。页脚保留现有复制、反馈、Fork 和恢复操作。
- 自动规划说明、思考、工具与步骤属于执行过程，汇总后按发生顺序查看；不显示 plan／production／Run 编号或阶段执行记录标题，也不删掉过程内容。
- 已成功提交的表单答案继续在原表单位置呈现。显式续做产生可见用户消息时，保留它和后续正式回复的先后；共享任务状态及过程汇总入口，不把晚发生的正式正文搬到这条用户消息之前。

运行中的结构示意：

    助手
    旋转图标  进行中  42s
    ▾ 执行记录
      思考、读取、自动规划说明、制作与检查动作（按时间顺序）
    需要用户确认的内容／问题（如有）

最终结构由同一个任务状态行结算、同一个执行记录默认收起；最终结论、产物面板和原有操作在记录外显示。

### 执行记录的折叠

- 一个展示任务最多有一个“执行记录”入口，由与任务状态相同的可见回复承载。后继物理消息、自动重试和明确恢复不另开入口，过程追加到同一时间线；不嵌套前序各 Run 的执行记录壳。
- 任务实际执行及自动衔接期间默认展开；等待回答、等待用户发起恢复以及任务最终结束后默认收起。规划的完成标记不能折叠正在继续执行的任务记录。
- 用户手动展开或收起后，切换 Run、明确恢复、刷新和重新进入会话均保留本任务的选择；普通新任务使用自己的默认规则。
- 自动生成的中间规划说明放入执行记录。需要用户确认的正式方案、提问表单、已回答结果、失败原因与恢复操作、最终结论和产物入口留在会话中的原有时间位置，始终在记录外。
- 执行记录是全任务的过程汇总，而不是某条回复的连续正文。跨可见用户消息汇总时，在记录内保留等待／收到答复／恢复等必要的时序节点，正式问答和结论仍在主会话按发生顺序展示。
- 工具、Todo、思考条目自己的状态与局部耗时继续展示；它们描述具体动作，不承担任务完成宣告。
- 没有工具或 Todo 的 Agent 仍能显示任务状态，不新增空的过程占位卡。

## 任务状态

| 条件 | 唯一任务状态 | 计时与反馈 |
| --- | --- | --- |
| 首次 Run 尚未实际开始 | 准备中 | 尚无执行时长时不显示假值 |
| 当前 Run 正在执行 | 进行中 | 持续累计 |
| 前序 Run 已结束，宿主已确认自动后继 | 进行中 | 衔接期间持续累计，不先显示完成 |
| 当前轮成功结束，并留下需要用户作答的问题 | 等待回答 | 冻结累计耗时，展示问题 |
| 答案／显式恢复已被宿主接受，后继尚未实际开始 | 准备中 | 保留已累计时长且暂不增长，不再提示用户回答 |
| 当前轮成功结束，仍有可继续的未完成工作 | 任务尚未完成 | 冻结累计耗时，保留“继续剩余任务” |
| 最后一次 Run 成功结束，且无待回答问题、无按现有规则判定的未完成工作 | 已完成 | 冻结累计耗时，显示结论与可用产物 |
| 当前最终 Run 失败 | 运行失败 | 冻结累计耗时，保留原因与恢复操作 |
| 用户停止且宿主确认当前执行结束 | 已取消 | 冻结累计耗时，保留已产生内容 |
| 断线但宿主尚未确认结束 | 保留最后已知任务状态 | 重连提示作为连接信息展示，不自行判失败或完成 |

状态首先看展示任务的当前有效执行：已经确认自动后继或当前 Run 活跃时，前序的成功、失败、取消和提问不覆盖当前状态。自动后继排队维持进行中；用户答复／显式恢复后的排队按上表显示准备中。

没有后继或活跃执行时，按当前有效最终结果依次判断：失败／取消 → 待回答问题 → 可继续工作 → 已完成。这里的失败／取消不包含已被同任务后继接续的历史结果。

完成标记必须属于最终当前 Run，规划的标记不能完成生产。文件存在不自动清除 Todo；“已完成”继续表示本次执行收尾，不新增产物质量验收含义。

## 累计计时

用户已确认：Run 切换不归零，自动衔接时间计入；等待用户回答时暂停。

- 起点是任务首个 Run 的实际执行开始，不是消息气泡创建或用户点击发送的时间。
- 自动续跑、排队衔接、可恢复的自动重试均属于同一连续执行段，期间计时不断。
- 进入等待回答时，执行段结束于当前 Run 的真实结束时刻；收到回答后，从后继 Run 实际开始时再累计。用户填写、提交以及提交后尚未开始执行的等待时间不计入。
- 进入最终完成、尚未完成、失败或取消时冻结。显式恢复若宿主仍关联为同一任务，保留已累计时长，从恢复 Run 实际开始时续计；宿主创建新任务则使用新的计时。
- 秒数每秒更新，使用现有耗时格式。刷新、重连、重新挂载不能建立新起点，旧快照不能覆盖较新的状态或计时。
- 连接正常且任务仍运行时按服务端事实连续计时。断线时保留最后已知状态，计时只作临时显示；重新获得权威起止后校准，最终值以宿主记录为准，不把离线推算写成执行事实。
- 缺少可信起止或暂停记录时，不把未知当作 0，不拿最后一个 Run 的耗时冒充任务总耗时；显示状态并省略总计时。完整事实到达后补上。

计量示例：规划 12 秒、自动交接 2 秒、生产 28 秒，总计 42 秒。若中途问答等待 5 分钟，该 5 分钟不加入；恢复前后仍累计为实际执行段的总和。

## 恢复与历史兼容

- 实时展示和历史回读都使用同一任务归属、当前 Run 和时长事实。重新打开会话不应多出中间完成状态、重复生产正文或重置计时。
- 刷新时仅拿到部分历史，先展示已知状态；拿到完整任务事实后收敛，不将局部历史当成任务全貌。
- 有任务归属但历史计时不完整：仍合并任务状态，省略总计时。
- 没有宿主任务归属的旧消息：保留原有单条消息展示，不猜测合并、不重写历史记录。
- 等待回答时暂停不依赖用户是否停留在当前会话。宿主明确接受回答后显示准备中，后继实际开始再显示进行中并续计。
- 宿主明确拒绝或确认未接受回答：保持等待回答、冻结计时、允许重试。
- 请求结果未知或仅创建响应丢失：保持最后已知任务状态，显示提交结果待确认的连接反馈；沿同一次提交核对或幂等恢复，不将网络异常当作尚未开始。确认已开始后按真实起点补计，确认拒绝后回到等待回答。
- 取消、失败与手动恢复的执行归属使用现有宿主结果；展示关联按本方案来源规则确认，不通过前端决定底层执行任务。

## 数据埋点

本次不新增产品行为或效果事件，不改动现有每次 Run 的时延、耗时和成功率口径。任务累计耗时仅是会话展示值；不能将它直接替换原有 Run 指标。展示是否正确由验收场景和记录对照验证，后续若需要线上衡量另定义增量。

## 评审结果

2026-10-13 完成产品、工程、测试三个独立 AI 角色的两轮评审，最终均通过，剩余必须修正项为零。
