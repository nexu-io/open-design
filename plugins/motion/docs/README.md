# OpenDesign 文档中心

`docs/` 保存产品为什么存在、服务谁、如何工作、如何验证价值，以及商业化方向。每次仓库需求都在这里更新相关事实与决策，使后续贡献者能接着已有理解推进。

本轮整理日期：2026-11-05。实现基线：OpenDesign 0.6.2候选版（一期公开9 Tool，真实模板Skill与macOS共享编辑器已整合），包含通用会话、Motion 模式、Artifact 浏览器与原生 Hyperframes 编辑器、统一 MCP/模板弹框、模板热度数据，以及 Studio/MCP 共用的模型网关与素材生成。产品现状以代码与验证证据为准；尚未验证的画像和商业化方案有单独标记。

## 每次需求的维护流程

1. **先建立上下文。** 阅读产品架构和相关专题，确认当前行为与用户问题。沿用已有需求信息、画像与决策，不重复发起已回答的确认。
2. **随实现更新。** 将变化写回对应的正式文档。接口或工程变更更新架构/工程专题，体验变更更新流程/设计专题，目标用户或商业边界变化更新画像/商业化专题。
3. **记录本次选择。** 在 `product/changes.md` 头部新增一个 `REQ-YYYYMMDD-序号` 条目。同一需求的连续修改补充原条目；新需求新建条目。至少说明问题、用户、前后行为、决策理由、文档影响与验证证据。
4. **保持入口同步。** 用户可见能力、安装方式、使用路径或限制变化时更新根 README。新专题加入本页索引。历史结论被替代时注明由哪条决策替代，不让旧方案继续充当当前事实。
5. **同批交付。** 需求的代码和文档在同一提交或 PR 内完成；直接提交也适用。PR 链接相关文档与需求 ID，交付说明列出实际检查。无需改动无关专题，但需求记录必须说明画像和商业化影响。

简单需求使用现有文档加一条记录即可。跨模块、长期或存在多方案取舍的需求，可将 [模板](templates/requirement.md) 复制到 `docs/requirements/YYYY-MM-DD-主题.md`，再由需求记录和本页链接过去。不要留下未填写的模板作为完成成果。

## 证据与状态

| 标记 | 含义 | 需要的依据 |
| --- | --- | --- |
| 当前已实现 | 当前分支/版本已经具备的行为 | 源码、版本或提交，以及实际验证结果 |
| 已确认方向 | 用户或维护者明确要求的产品原则 | 需求记录或可访问的决策来源；不表示已经实现 |
| 待验证假设 | 关于人群、痛点、价值、渠道或付费的推断 | 假设、验证方法、负责人角色、下一步 |
| 候选方案 | 尚未选择或交付的实现与商业选项 | 解决的问题、成本、取舍与采用条件 |

指标记录口径、观察窗口和来源；没有样本时写“待采集”。价格、营收、转化率、客户数量和市场规模不能用猜测填成事实。SAP 等尚未确认的术语保留原称呼与工作定义，后续确认后在画像及需求记录中同步更正。

产品文档不保存密钥、个人安装路径或客户私有素材。研究结论应附可访问出处和采集日期；模板平台热度是原帖数据快照，不能充当 OpenDesign 的用户指标。

## 文档交付检查

- 正式专题反映最终实现，需求记录保留选择理由与证据。
- 文件路径、相对链接、版本、能力状态和术语一致。
- 已实现能力与候选商业方案分开，未执行的检查如实标注。
- README、AGENTS.md、CLAUDE.md 与 PR 中的文档入口可访问。

纯文档修改检查链接、内容与 `npm run check` 即可；涉及打包清单时检查插件包含的文档。涉及代码的需求再运行与变更相关的类型、测试和浏览器验证，不为文字变更重跑无关渲染。
